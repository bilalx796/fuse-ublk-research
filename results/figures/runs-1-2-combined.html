Runs 1 + 2 combined · Emulab d430 · Linux 6.8 · 31 Oct & 8 Nov 2026

How much overhead do FUSE and ublk add, where does it come from, and when does it matter?

Every FUSE or ublk setup is compared with the same storage path without the userspace layer. All devices are RAM-backed, so the layer sets the cost and the disk does not hide it. Tests are fio microbenchmarks; no application (RocksDB) yet.

Kernel only (baseline) ublk FUSE

µs = microsecond (one millionth of a second). Medians of 3–5 repeats × 20 s. Latency = total time per request. CPU = busy time on all CPUs (fio + server + kernel) per request. Each section is tagged with the run its data comes from.

What we know now
  • A small read costs ~2 µs in the kernel, ~12 µs through ublk, ~38 µs through FUSE. Run 2 reproduced this within ~5% on a different machine.
  • The cost is the round trip to the userspace program: about 4 context switches per request, against none in the kernel.
  • Many requests at once hide the delay, not the CPU. At 32 in flight, speed nearly matches the kernel, but FUSE still uses ~4.5× its CPU per request and ublk ~2×.
  • With several senders, large requests expose both layers. FUSE falls to 1/3–1/2 of ext4; ublk is capped by copying every byte on its 4 server threads.
  • Two puzzles solved: slow ext4-on-ublk writes are an ext4 completion worker, and FUSE's no-cache collapse is a size check before every read.
Finding 1 · What is the overhead run 1, confirmed in run 2

One small read takes ~2–3 µs in the kernel, ~12–16 µs through ublk, ~38 µs through FUSE

Why. With the kernel only, the read finishes inside one system call on one CPU. With ublk or FUSE, a separate program must wake up, do the work and reply, and then fio must wake up again: about 4 context switches per request, against 0 for the kernel. FUSE also does a second, real read into ext4 for every request.

Is it stable? Run 2 repeated the ublk null and RAM-disk setups 5 times on a new node: 12.0 → 12.2 µs and 80.0k → 78.5k reads/s for ublk, 422k → 413k for the RAM disk.

Finding 2 · Cost of each layer run 1

FUSE adds about 3× more time and CPU per request than ublk

Extra CPU per 4 KB read (µs)

How to read it. Each bar is one setup minus its matching kernel baseline. "ublk interface" (ublk null minus null_blk) is the cleanest measure of ublk itself, because its server does no I/O at all. The loop and FUSE bars also include the server's own I/O into the RAM disk.

Where FUSE's extra goes. In the profile, the FUSE daemon's top kernel function was clear_page_erms (zeroing fresh memory pages) from libfuse's splice path, above the data copy itself. Turning splice off made small reads ~20% cheaper but large reads up to 10× slower, so it is a trade-off, not a fix.

Finding 3 · Hidden cost run 2

With 32 requests in flight, speed nearly catches up, but CPU per request does not

4 KB reads per second (thousands)

CPU per 4 KB read (µs)

Why. With many requests waiting, the server handles several per wake-up, so the delays overlap and throughput lands within ~10–25% of the kernel. But every request still has to be passed out, handled and answered. FUSE uses ~4.5× the CPU of ext4 per request and ublk ~2× its baseline. On a busy machine that CPU is taken from applications, even when the benchmark looks fine.

Finding 4 · Large requests run 2

With four senders, large requests run at a fraction of the kernel's speed through either layer

ublk interface (vs null_blk) ublk loop (vs RAM disk) FUSE over ext4 (vs ext4)

The run-1 surprise was a test artifact. In run 1, FUSE looked faster than ext4 on 128 KB reads. With a single fio job, ext4 copies every byte on that job's one CPU and stays near 37k/s at any depth, which is what FUSE "beat" (the 191% bar). With four jobs, ext4 scales to ~140k/s and FUSE does not.

ublk is capped by copying. ublk's 4 queue threads copy every byte between the kernel and the server, and Linux 6.8 has no zero-copy for ublk. Those 4 server CPUs set the ceiling. FUSE's slowest 1% of 128 KB reads took ~3.5 ms, against 0.25–0.9 ms for ext4.

Noise fixed. The RAM-disk baseline here was re-run 5 times on 8 Nov (145–147k and 142–144k reads/s, under 1% spread). Earlier repeats had varied ~40%.

Finding 5 · FUSE settings run 2

Every FUSE setting trades one thing for another

One read at a time: median latency (µs)

8 reads in flight: reads per second (thousands)

  • One worker thread (--single): each request is ~30% faster and uses ~37% less CPU, but one thread caps out at ~113k reads/s under load.
  • Four worker threads, one per server CPU: the slowest 1% of requests drop from 108 to 48 µs, for ~20% less throughput under load.
  • --clone-fd: no measurable effect.
  • No caching (--nocache): reads collapse under load. Explained in Finding 7.

Finding 6 · Puzzle solved run 2

Writes through ext4 on ublk are slow because of one extra kernel worker per write

Not the journal. ext4 with the journal turned off gives the same numbers, and the disk saw no extra writes (its write count matched fio's).

What it is. Tracing every task wake-up during the writes showed exactly one extra one per write: a kernel worker running iomap_dio_complete_work, 81,902 times for 81,902 writes. Reads and raw ublk writes have none. ext4 hands the "write finished" step to a worker whenever the device finishes later rather than immediately, which ublk does and the RAM disk does not. This is a cost of ext4 on any such device, not of ublk itself.

Finding 7 · Puzzle solved run 2

With caching off, FUSE checks the file's size before every read, and reads stop overlapping

Default settings Caching off (--nocache)

What it is. With caching off, Linux asks the FUSE program for the file's attributes (a GETATTR request) before every read, and waits for the answer. Kernel probes counted exactly 1.00 GETATTR per read. Because fio's submitting thread waits on it, at most 2 FUSE requests were ever in flight instead of 8, so 8-deep reads behave like 1-deep reads that each pay two round trips. Writes skip the check and are unaffected.

Likely fix (not tested). A non-zero attribute timeout, or opening files in FUSE's direct-I/O mode, which skips that check.

Short diagnostic runs (8 s) with tracing on, so absolute speeds are lower than in the other charts. Compare the two bars in each row, not across sections.

What these results do not show yet

  • Real applications. Only fio so far. RocksDB put/get is planned.
  • Real disks. An SSD's own ~10–80 µs per request may hide much of this overhead.
  • Newer Linux. 6.8 lacks FUSE passthrough, FUSE over io_uring and ublk zero-copy, which target exactly these costs.
  • Breadth. One machine type, 20 s runs, 3–5 repeats. There's no FUSE "null" filesystem yet to isolate FUSE's interface cost the way ublk null does for ublk.
