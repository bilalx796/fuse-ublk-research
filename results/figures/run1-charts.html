What does it cost to serve storage from userspace?

We timed the same fio workloads on plain kernel storage, on ublk (a block device served by a userspace program), and on FUSE (a filesystem served by a userspace program). All storage is in RAM, so the differences come from the software layers, not from disk speed.

Kernel only (baseline) ublk FUSE

Medians of 3 repeats × 20 s. Latency = total time per request. CPU = busy time on all CPUs (fio + server + kernel) per request.

Finding 1 · What is the overhead

One small read takes ~2–3 µs in the kernel, ~12–16 µs through ublk, ~38 µs through FUSE

Why this probably happens

  • With the kernel only, the read is finished inside one system call on one CPU. Nothing has to wake up.
  • With ublk or FUSE, the request is handed to a separate program. That program must wake up, do the work, and reply, and then fio must wake up again. We counted about 4 context switches per request for both, versus 0 for the kernel.
  • FUSE does more work per request: the daemon reads the request from /dev/fuse, does a second, real read into ext4, then writes the reply back. ublk's null target does no second I/O, and its loop target uses io_uring to batch the reply with fetching the next request.

How to read it. Each bar is one setup minus its matching kernel baseline. "ublk interface" (null target minus null_blk) is the cleanest measure of ublk itself. The loop and FUSE bars also include the server's own second I/O into the RAM disk.

Why CPU is higher than latency for FUSE. Several CPUs work on each request (fio, the FUSE daemon thread, kernel wake-up work), so the total CPU time per request can be larger than the time the request takes from start to finish.

Finding 2 · Where the FUSE time goes

A surprising share of FUSE's cost is zeroing memory, not moving data

Splice on (default) Splice off (--nosplice)

CPU µs per request, reads only (direct writes fail with splice off).

What we saw. In the FUSE daemon's profile, the top kernel function was clear_page_erms (filling fresh memory pages with zeros), above the actual data copy. With splice turned off (--nosplice) it disappeared, and a small read got ~20% cheaper in CPU.

Likely explanation. libfuse's splice path moves data through a kernel pipe and seems to set up fresh pages for each request. For small requests that setup costs more than the copy it saves. For large requests (128 KB) the copy it avoids is big, so turning splice off made large reads up to 10× slower. Splice off also broke direct writes: the unaligned userspace buffer is rejected by ext4.

Finding 3 · When it matters

The slowdown is worst for small requests sent one at a time

ublk interface (vs null_blk) ext4 on ublk loop (vs ext4) FUSE over ext4 (vs ext4)

Why. With one request at a time (qd1), every request pays the full round trip to userspace and nothing overlaps, so throughput drops to 5–20% of the kernel's. With 8 requests in flight (qd8) the userspace server is busy all the time and the wake-up costs overlap, so throughput gets close to the kernel's.

Bars above 100%. At 128 KB with 8 in flight, FUSE and ublk beat their baselines. This is a side effect of the test, not real speed: with one fio job, the kernel-only path copies every byte on fio's single CPU, while FUSE and ublk spread the copying across 4 server threads on 4 CPUs. They still use more total CPU.

Finding 3b · Hidden cost

Sending more requests at once hides the delay, but not the CPU cost

1 request in flight (qd1) 8 requests in flight (qd8)

Why. At qd8 the server handles several requests per wake-up, so fewer context switches are paid per request and the extra CPU per request falls (FUSE 45 → 12 µs, ublk 9 → 2 µs). But it doesn't reach zero: each request still has to be parsed, copied and answered by the server. On a busy machine that CPU is taken from applications, even when the benchmark's throughput looks fine.
